# NoteWeave 项目规范文档

## 1. 目标

本文档用于约束 NoteWeave 后续开发方式。项目主要由 Codex 在 goal 模式下持续开发，因此规范不追求复杂流程，而是保证长期运行时能恢复上下文、控制变更范围、稳定验证结果，并用 git 形成清晰检查点。

## 2. 基本原则

1. 需求以 `docs/需求文档.md` 为准，架构以 `docs/架构文档.md` 为开发蓝图。
2. 优先完成可运行、可演示的 MVP 闭环，再补充高级能力。
3. AI 能力只通过 API 接入，不引入本地模型、OCR、GPU、向量库等重依赖作为主路径。
4. 每次开发尽量形成可验证的小闭环：实现、运行、自检、记录。
5. 不做无关重构，不照搬 MoDora 的重依赖链路。

## 3. 目录约定

推荐项目结构：

```text
NoteWeave/
  backend/
    pyproject.toml
    src/noteweave/
    tests/

  frontend/
    package.json
    src/

  frontend-old/
    旧版无构建链前端，仅作参考和回滚资料

  docs/
    需求文档.md
    架构文档.md
    项目规范文档.md
    开发日志.md

  README.md
```

约定：

1. `MoDora/` 只作为参考项目，不在 NoteWeave 主应用中直接依赖。
2. 后端主包名使用 `noteweave`。
3. 文档放在 `docs/`。
4. 长期开发过程中的重要进展、未完成事项和验证命令记录到 `docs/开发日志.md`。

## 4. uv 环境规范

后端 Python 项目统一使用 `uv` 管理虚拟环境和依赖。

开发前置：

```bash
uv --version
```

如果本机没有 `uv`，先安装 uv。安装方式不写死到项目脚本里，避免在受限环境中自动下载。

后端初始化和使用命令：

```bash
cd /root/project/NoteWeave/backend
uv venv
source .venv/bin/activate
uv pip install -e ".[dev]"
uv run pytest
uv run uvicorn noteweave.api.app:app --reload
```

依赖管理规则：

1. 新增 Python 依赖必须写入 `backend/pyproject.toml`。
2. 不直接用系统 Python 跑项目命令，统一使用 `uv run ...`。
3. 不把 `.venv/` 提交到 git。
4. MVP 阶段后端依赖保持轻量：FastAPI、Pydantic、SQLAlchemy/SQLModel、测试工具即可。
5. 不引入 PaddleOCR、transformers、lmdeploy、opencv、chromadb 等重依赖，除非后续明确作为可选扩展。

## 5. Git 版本管理规范

项目必须用 git 做版本管理。

### 5.1 基本流程

每个开发切片开始前：

```bash
git status --short
```

每个可运行阶段结束后：

```bash
git status --short
git diff --stat
```

确认自检通过后再提交：

```bash
git add <changed-files>
git commit -m "type(scope): summary"
```

### 5.2 提交粒度

提交应按功能切分：

1. `docs:` 文档变更。
2. `feat(backend):` 后端功能。
3. `feat(frontend):` 前端功能。
4. `test:` 测试补充。
5. `fix:` 缺陷修复。
6. `chore:` 构建、配置、依赖和工程化调整。

示例：

```text
docs: add project development conventions
feat(backend): add course and knowledge tree APIs
test(backend): cover note search indexing
```

### 5.3 长期运行检查点

goal 模式可能持续多轮，存在上下文压缩、中断、半成品遗留等风险。因此：

1. 完成一个可运行切片后，应尽快形成 git commit。
2. 大改动前先确认当前工作区状态，避免覆盖用户或历史变更。
3. 不在大量未提交变更上继续堆功能。
4. 每次中断或阶段结束，在最终回复中说明已改文件、验证命令和未完成项。
5. 对跨轮任务，优先依赖 git 历史、当前文件和 `docs/开发日志.md`，不依赖记忆。

## 6. 开发日志规范

`docs/开发日志.md` 用于长期开发恢复上下文。每个阶段记录：

```text
日期：
目标：
完成：
验证：
遗留：
下一步：
```

记录原则：

1. 只写事实，不写长篇过程。
2. 验证命令要能复跑。
3. 遗留问题必须具体到模块或文件。
4. 如果某项能力只是 mock 或降级实现，必须明确标注。

## 7. 后端开发规范

后端采用分层结构：

```text
api -> core.services -> core.domain / core.interfaces <- infra
```

约定：

1. API 层只处理请求、认证依赖、响应模型和错误码。
2. 业务规则放在 `core/services`。
3. 数据库访问封装到 repository 或 infra 层。
4. AI、文件存储、搜索索引等外部能力通过接口隔离。
5. 权限校验必须在写操作和私有内容读取前执行。
6. AI 失败不能阻塞基础笔记、错题、共享和检索功能。

MVP 优先顺序：

1. 认证与用户。
2. 课程与成员。
3. 知识树。
4. 笔记和错题。
5. 共享互动。
6. 关键词检索。
7. AI 摘要和标签建议。

## 8. 前端开发规范

前端以可演示为优先：

1. 前端使用 Vue 3 + Vite + TypeScript，入口为 `frontend/index.html`，源码放在 `frontend/src/`。
2. Landing 页面用于介绍功能，工作台通过 `#workspace` 进入。
3. 课程、知识树、笔记、错题、搜索是核心导航。
4. 借鉴 MoDora 的三栏布局：左侧导航、中间主工作区、右侧详情/AI/评论面板。
5. 知识树可使用原生树列表交互，树节点必须能进入节点详情、笔记列表和错题列表。
6. 富文本编辑器先保证文本、代码、公式、图片；思维导图可作为 P1/P2。
7. 旧版前端保留在 `frontend-old/`，新开发不再修改旧版文件，除非明确做迁移参考。

前端验证命令：

```bash
cd /root/project/NoteWeave/frontend
npm run typecheck
npm run build
```

## 9. 测试和验证规范

每个后端切片至少做一种验证：

1. 单元测试。
2. API 测试。
3. 使用 `TestClient` 的端到端流程测试。
4. 临时 smoke script，后续转成正式测试。

推荐后端验证命令：

```bash
cd /root/project/NoteWeave/backend
uv run pytest
```

如需启动服务：

```bash
cd /root/project/NoteWeave/backend
uv run uvicorn noteweave.api.app:app --reload --port 8000
```

验证完成后，在回复或开发日志中记录实际运行结果。

## 10. 数据和安全规范

1. 密码不得明文存储。
2. API key 只放环境变量或本地未提交配置文件。
3. 上传文件限制类型和大小。
4. 个人笔记和课程共享笔记必须做权限区分。
5. 删除章节或知识点前必须检查关联内容。
6. 采纳纠错或补充时必须留下版本记录或审计记录。

## 11. AI 功能规范

AI 能力遵循可选增强原则：

1. 默认不要求本地模型。
2. 远程 API 配置缺失时，AI 接口返回明确状态或使用本地规则降级。
3. AI 生成的摘要、标签、知识树建议必须进入待确认状态。
4. 用户采纳后才写入正式笔记元数据或标签。
5. 测试中使用 mock model client，不依赖真实 API。

## 12. 中断恢复规范

如果开发中断或上下文被压缩，恢复时按以下顺序判断真实状态：

1. `git status --short`
2. 最近 git commit 和 diff
3. `docs/开发日志.md`
4. 当前代码和测试结果
5. 需求文档和架构文档

恢复后先完成最近一个未闭合切片，不重新发散设计。

截至本文档创建时：

2. `uv` 是项目要求的 Python 环境管理工具。
3. 当前环境中如果 `uv --version` 不可用，需要先安装 uv 后再开始后端开发。
